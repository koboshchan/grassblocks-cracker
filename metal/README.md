Native grass texture solver

Keep grass_solver source and solver_common.h together. Both solvers accept browser formation.txt downloads unchanged. A file begins with a positive observation count followed by that many rows of x y z rotation is_side. Coordinates are relative signed int32 offsets, including individual heights. Rotation is 0..3 for tops, 0..1 for sides; is_side is 0 or 1. Blank lines and # comments are accepted anywhere. Extra fields after the five row values, such as confidence=0.95, are ignored. Missing files, empty formations, truncated rows, extra rows, invalid numbers and unsupported rotations fail explicitly. There is no fallback formation.

Run with --formation FILE and --north 0|1|2|3|all, followed optionally by six inclusive positional bounds xmin xmax ymin ymax zmin zmax. Defaults are -6000 6000 60 256 -6000 6000. Bounds and every offset addition are checked before GPU work. Volumes that overflow uint64 are rejected.

The north convention here transforms relative x,z as n0 (x,z), n1 (-z,x), n2 (-x,-z), n3 (z,-x), and adds n to rotation modulo 4 (modulo 2 for sides). --north all searches these four interpretations separately. Do not apply a north rotation twice. Old auto-formation-20261101/auto.html exported already-transformed world-relative coordinates and uses the inverse direction for its north selector. Use --north 0 for its already oriented exports. New browser downloads must use raw observations for this CLI north convention; explicit previously world-oriented exports also use --north 0.

Stdout contains only x y z north, one candidate per line. Stderr reports progress, measured candidates/second, match count and final total tested. Redirect stdout to a file for sparse or very large result sets. All matches are emitted, with no 100-result cap. Each dispatch evaluates at most 4194304 candidate origins. Sparse output reserves one index per candidate plus a counter, so even a match at every origin cannot overflow. The host reads and sorts only matched indices, not a dense flag array. Ctrl+C stops between dispatches, prints partial totals and exits 130. A GPU command already in flight must finish first. Check exit status before treating output as a complete search.

Each origin uses the modern vanilla Java block-coordinate hash: signed int32 x*3129871 wrap before long extension, signed int64 z*116129781, xor with y, wrapping 64-bit l*l*42317861+l*11, then Java Random's first nextInt(4), modulo 2 for sides. Arithmetic uses fixed-width types on CUDA, including Windows where long is only 32 bits. Distinct north labels are distinct interpretations; no deduplication across north labels is attempted.

Build on macOS with Xcode command-line tools using clang++ -std=c++17 -O3 -fobjc-arc grass_solver.mm -framework Foundation -framework Metal -o grass_solver.

Only tiny GPU workloads are used.

Metal runtime autotuning

The Metal CLI defaults to --autotune auto. On a cache miss it measures 16 real dispatch configurations, threadgroup widths 64/128/256/512 crossed with 1/2/4/8 items per GPU thread, subject to the device's limits. These are runtime values in the actual search kernel, not labels over identical launches. Threads evaluate strided, non-overlapping candidate indices and handle partial batches without losing or duplicating origins.

Tuning uses the loaded, north-oriented observations and the requested search dimensions. It samples up to 262144 origins at the beginning, middle and end of the real search. Every variant is warmed up first. Three interleaved, permuted rounds use Metal GPU timestamps, with wall timing only as an older-OS fallback. The lowest median sample time wins. Sorted match-index sets from every measured dispatch must equal the baseline, with explicit range/duplicate/capacity checks and poisoned output memory. Independent Python-oracle regressions additionally verify the arithmetic and output mapping. Benchmark results go only to stderr and never appear as search matches.

Timings are persisted at ~/Library/Caches/grass-solver/metal-autotune-v2.plist. Cache identity includes GPU name and architecture, OS version, SIMD/threadgroup limits, full embedded kernel-source hash, exact oriented formation, search dimensions and minimum bounds. Changing a workload or kernel therefore requires a fresh measurement. Auto mode skips tuning for tiny searches below 32768 origins, unless a valid cache already exists. --autotune force benchmarks even with a valid entry and for tiny searches. --autotune off skips both tuning and cache lookup, using width 128 (or the hardware maximum if smaller) and one item per thread.

--clear-autotune-cache removes the selected cache before solving; combine it with --autotune off to clear without repopulating. --autotune-cache FILE overrides the location. GRASS_METAL_AUTOTUNE_CACHE provides the same override through the environment; the CLI takes precedence. Cache writes are atomic. Invalid/corrupt cached entries are rejected, and cache write failures do not stop a valid search. Up to 64 workload entries are retained, then the metadata is reset. Concurrent processes may replace each other's timing entries, which affects only cache efficiency, not solver correctness.

Run python3 test_solver.py ./grass_solver --autotune force, repeat with --autotune off, then run python3 test_autotune.py ./grass_solver. The latter exercises real force/auto/off launches, persistent-cache reuse, shape invalidation, forced remeasurement, clearing, corrupt and invalid entries, environment/CLI paths, save failures and non-divisible batch tails. It searches 1008005 hill origins and requires the exact sole result 3538 90 -454 0 in every path.

The final kernel uses xz-column tasks with inner y loops for dimensions y<=4096 and z<=UINT32_MAX-4194304, amortizing 32-bit division over the column. Partial first/last columns are bounded exactly. Wider dimensions use the original 64-bit linear decoder, so large int32 coordinate domains remain supported. GRASS_METAL_FORCE_WIDE=1 exercises this fallback for regression tests and has a distinct cache identity. Hash arithmetic uses exact uint-pair products with Metal mulhi, preserving all required 64-bit polynomial and 48-bit LCG bits. No approximate/truncated-coordinate hash is used. Tops are stably tested before less-selective side observations.
