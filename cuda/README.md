Native grass texture solver

Keep grass_solver source and solver_common.h together. Both solvers accept browser formation.txt downloads unchanged. A file begins with a positive observation count followed by that many rows of x y z rotation is_side. Coordinates are relative signed int32 offsets, including individual heights. Rotation is 0..3 for tops, 0..1 for sides; is_side is 0 or 1. Blank lines and # comments are accepted anywhere. Extra fields after the five row values, such as confidence=0.95, are ignored. Missing files, empty formations, truncated rows, extra rows, invalid numbers and unsupported rotations fail explicitly. There is no fallback formation.

Run with --formation FILE and --north 0|1|2|3|all, followed optionally by six inclusive positional bounds xmin xmax ymin ymax zmin zmax. Defaults are -6000 6000 60 256 -6000 6000. Bounds and every offset addition are checked before GPU work. Volumes that overflow uint64 are rejected.

The north convention here transforms relative x,z as n0 (x,z), n1 (-z,x), n2 (-x,-z), n3 (z,-x), and adds n to rotation modulo 4 (modulo 2 for sides). --north all searches these four interpretations separately. Do not apply a north rotation twice. Old auto-formation-20261101/auto.html exported already-transformed world-relative coordinates and uses the inverse direction for its north selector. Use --north 0 for its already oriented exports. New browser downloads must use raw observations for this CLI north convention; explicit previously world-oriented exports also use --north 0.

Stdout contains only x y z north, one candidate per line. Stderr reports progress, measured candidates/second, match count and final total tested. Redirect stdout to a file for sparse or very large result sets. All matches are emitted, with no 100-result cap. Each default dispatch evaluates at most 4194304 candidate origins. A uint32 append index buffer has one slot per origin, so the mathematical maximum match count always fits. Only actual matches are copied back, eliminating dense device-to-host flag traffic without any capped-result loss. Formation rows use constant memory up to 1024 observations, otherwise global memory. Tops are stably ordered before sides for higher early rejection. Ctrl+C stops between dispatches, prints partial totals and exits 130. A GPU command already in flight must finish first. Check exit status before treating output as a complete search.

Each origin uses the modern vanilla Java block-coordinate hash: signed int32 x*3129871 wrap before long extension, signed int64 z*116129781, xor with y, wrapping 64-bit l*l*42317861+l*11, then Java Random's first nextInt(4), modulo 2 for sides. Arithmetic uses fixed-width types on CUDA, including Windows where long is only 32 bits. Distinct north labels are distinct interpretations; no deduplication across north labels is attempted.

Build on Linux with a CUDA toolkit and supported C++ compiler using nvcc -std=c++17 -O3 -arch=sm_89 grass_solver.cu -o grass_solver. Change sm_89 for your GPU if needed.

Build on Windows from the x64 Native Tools Command Prompt with nvcc -std=c++17 -O2 -arch=sm_89 grass_solver.cu -o grass_solver.exe. Use a Visual Studio release supported by your installed CUDA toolkit. This desktop has CUDA 12.1 and VS 2026, so the actual successful test build required -allow-unsupported-compiler -D_ALLOW_COMPILER_AND_STL_VERSION_MISMATCH. Those overrides are an observed local compatibility workaround, not a general compatibility guarantee.

Run ./grass_solver --formation fixtures/hill22.txt --north all 3535 3541 88 92 -457 -451. On Windows use grass_solver.exe instead. Expected sole output is 3538 90 -454 0.

Run python3 test_solver.py ./grass_solver, or python test_solver.py grass_solver.exe on Windows. Tests compare exact candidate sets with an independent arbitrary-precision Python oracle, including negative and large wrapped coordinates, mixed heights, side textures, every north, 5043 dense results and malformed/overflow inputs. Only tiny GPU workloads are used.

Actual Windows RTX 4070 Super compile and runtime regression passed November 1, 2026. The compiler used C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v12.1\bin\nvcc.exe with VS 18 Community vcvars64.bat. Test details are in TEST_LOG.txt. No encoder, Docker or training processes were changed.


Runtime tuning defaults to --autotune auto. Use --autotune force to remeasure or --autotune off for deterministic 128-thread, one-item defaults. GRASS_THREADS (32..1024, warp multiple) and GRASS_ITEMS (1..8) explicitly override and bypass tuning; GRASS_BATCH (256..16777216) controls bounded dispatch size. Automatic tuning measures 12 configurations, 64/128/256/512 threads with 1/2/4 consecutive candidates per thread, using CUDA events over three measured launches after a warmup. Every configuration's sorted result indices must exactly agree on the identical subset. The fastest measured kernel configuration is selected. Clock noise means close configurations may change between runs; this is real measurement, not a promise of globally optimal performance.

The cache is under LOCALAPPDATA/.grass-solvers on Windows or HOME/.grass-solvers on Linux. Its key includes GPU name, SM architecture, kernel version, y/z shape and exact oriented formation. A force run replaces that entry; deleting the entry clears it. Cache writes are optional and failures do not prevent solving. Progress and final search rates exclude device initialization and quick-start tuning; external wall-clock includes them. Very small searches can spend more time tuning than solving, so --autotune off is useful for regression tests.

CUDA arithmetic retains wrapping uint64 operations. A low-32-only polynomial is NOT equivalent: polynomial bits 16..63 feed the 48-bit LCG seed, and all lower seed bits can carry into the output bits 46..47 on multiplication. No such truncation was adopted. --use_fast_math is optional and provides no mathematical advantage for this all-integer kernel.

Actual 4070 Super benchmark on November 1, 2026 used the included hill22 formation, inclusive x/z -5000..5000, y 60..128. That is 6,901,380,069 candidate origins per north, not coordinate columns. Initial GPU utilization was 3–4% with 1068 MiB used and no compute training jobs. Original flag-buffer solver measured 3.90925 seconds, 1.7654 billion origins/s. Optimized sparse-buffer solver measured 0.233125 seconds, 29.6038 billion origins/s before runtime tuning. A forced tuned run measured 0.224159 seconds, 30.7879 billion origins/s, approximately 17.4x baseline. These are search-loop wall times, not just CUDA-event kernel timings. Original and optimized outputs were byte-identical, sole candidate 3538 90 -454 0.

The four-north run tests 27,605,520,276 origins total. Representative force and subsequent cache-hit times were 0.861909 and 0.840253 seconds, 32.0283 and 32.8538 billion origins/s. The selected launch was 128 threads and four items; all 12 autotune outputs agreed. Other runs selected 64 threads/four items due to close event timings. Event-only microbenchmark rates are higher than whole-search rates and are NOT interchangeable. See BENCHMARK.txt.

For a fat binary supporting Ada sm_89 plus RTX PRO 6000 Blackwell sm_120, use CUDA Toolkit 12.8 or later:
nvcc -std=c++17 -O3 -gencode arch=compute_89,code=sm_89 -gencode arch=compute_120,code=sm_120 -gencode arch=compute_120,code=compute_120 grass_solver.cu -o grass_solver
For a Blackwell-only build use -arch=sm_120. No Blackwell hardware was benchmarked or tuned in this local validation. Its runtime autotuner will measure locally on first use.
Official NVIDIA CUDA 12.8 release notes confirm SM_120 compiler support was introduced there:

For a stronger arithmetic regression, compile hash_oracle.cu with the same nvcc options and run python test_hash.py grass_hash_oracle.exe (or ./grass_hash_oracle on Linux). This compares 100,000 deterministic full-range int32 coordinate triples and top/side choices against an independent Python Java-semantics oracle. Actual RTX 4070 Super test passed.
